## Minimal informational story and application seams

Fixed English story: a fictional peer owns Service Rowan Support Terms. Producer PURE Work parses its own bounded document and derives the support-call price. Radik owns only base price20 and two support calls. Baseline actual Work yields NEEDS_SUPPORT_PRICE; admitted revision1 unit price3 changes actual consumer Work to total26; revision2 unit price4 yields total28. A fixed `RadikSupportTermsV01` profile adds publisher, recipient, document digest and derived terms to the common body fields; the profile validates arithmetic/document extraction and the declared support-task scope. The ordinary entry/supervisor should orchestrate two actual peer processes with independent roots, state, in-memory keys, inherited pipes and finite file-read fences. ## Restart, revision and refusal design

- The receiver's trust anchor is frozen from the independently observed peer bootstrap before any body. Issuer/key data in an incoming descriptor cannot establish or replace trust.
- Persist a separate application current-source high-water keyed by publisher/source record, updated only after the relevant signed/current descriptor, status and body admission. `ImportStore` high-water is per publisher/pointer/stream; its source map alone does not reject an older source revision. Preserve old entries; reject any attempted older revision before Work.
- Persist authenticated REVOKED/SUPERSEDED entries via `.observe()` before current-use refusal. End and reap receiverB1; start B2 with the exact persisted high-water/import/history/budget state, a new local signer and trusted operator repinning for the publisher. Verify old source revision and old ACTIVE status separately; no JSON Root/Host restoration.
- Acquire request and STATUS immediately before consumption. Their maximum60second lifetime is not a preparation budget. Keep sourceTTL300seconds and obtain a fresh legitimate source revision when required; never extend old envelopes.
- Use a separate declared AUDIT-only or disclosure-denied task context. The publisher must return signed REFUSED with body=None and manifest=None; receiver counters and allowed reads prove no body consumption. Private canary content and its hash remain outside reportable evidence.
- Signed-byte mutation, wrong issuer/anchor and wrong scope controls must start from otherwise current lawful material, so their intended guard is not hidden by request/source expiry. Controlled future-clock expiry checks are explicitly negative controls, not claims of actual elapsed expiry.

## Separate bounded engineering selector

`engineering_probe_v01` selects `app.external_drs_probe.peer`; it does not call the owner scenario. Distinct task, source, object and Root identifiers bind one actual producer Work and one actual consumer Work. The fresh signed exchange tests disclosure refusal, body integrity, independent-anchor and scope refusal, explicitly controlled expiry, persisted authenticated revocation and old ACTIVE replay after a genuinely restarted recipient. Its revision-high-water test is an explicitly mechanical state fixture and establishes no second-revision source authority or owner consumption. `external_drs_owner_v01` remains the complete prospective owner scenario.

Both entry functions accept the keyword `task_selector` and reject the other selector. Their initial public-key message and two-recipient-session protocol are identical structurally, with mode-specific DONE statuses. The master `scenario.json` contains a separate `engineering_probe_v01` block; each peer receives only its own document or local task input. All key capabilities are generated inside the corresponding peer and never serialized.

Each native one-item Work retains its actual-start UTC snapshot and refuses all trusted-source reads, pre-dispatch checks and final acceptance outside the original half-open 60-second proposal window. Final Root review uses that same nonrenewed window. A fresh Host is created per Work; this does not claim that the public PURE executor refreshes source state per instruction.
